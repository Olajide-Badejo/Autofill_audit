# ADR 0001: Toolchain resolution

Date: 2026-08-25

Status: accepted

## Context

The build specification names no version number for any package, on purpose: a
version written into a design document is stale the moment it is written, while
a resolution *rule* is not. The rule is to pin the newest stable release of
every dependency, resolved on the target machine at P0, and to record the result
here, in `pyproject.toml` as lower bounds, and in a committed lock file.

For the interpreter the rule is narrower: the newest stable CPython that
Playwright, scikit-learn, onnxruntime, and `ml-experiment-triage` all support.
onnxruntime is historically the last of the four to publish wheels for a new
CPython minor, so the intersection sitting one minor behind the newest CPython
would have been an expected and acceptable outcome.

The report engine has its own rule: `tectonic` preferred, with `latexmk` plus
TeX Live as the fallback when a full TeX installation is already present.

## Decision

### Interpreter

`/usr/bin/python3.14`, CPython `3.14.4`, with the project virtual environment at
`~/.venvs/autofill-audit` created from it.

The intersection did not sit behind the newest CPython this time. onnxruntime
publishes `cp314` wheels, so all four constraints are satisfied at the newest
stable minor. `ml-experiment-triage` requires `>=3.12` and is compatible.

`requires-python` in `pyproject.toml` is set to `>=3.14`, matching the only
interpreter this project has been tested against. Widening it is a deliberate
later decision that comes with a CI matrix entry, not a guess made now.

### CLI framework: click

The specification allows `typer` or `click`. click is chosen because the command
surface has nested groups (`corpus generate`, `corpus validate`), repeatable
options (`--format`, which may be given more than once), and a
`CliRunner`-driven test path that is the thing being asserted in CI. typer is a
layer over click that would buy annotation-driven signatures and cost a
dependency and one level of indirection when a flag misbehaves. There is no
third argument; this is a small decision recorded so it is not reopened.

### Task runner: Makefile

The specification allows a `Makefile` or a `justfile`. Make is chosen because it
is present on every Linux machine and on every GitHub Actions runner without an
install step, and because the value being sought here is that CI and a human run
the identical command. A runner that must itself be installed before the gates
can run weakens exactly that property.

### Lock file: `requirements.lock` via pip-compile

`pyproject.toml` carries lower bounds equal to the resolved versions above.
`requirements.lock` carries the fully resolved pin set, generated by pip-compile
from the `dev` and `llm` extras and committed. CI installs from the lock and
then installs the project itself with `--no-deps`, so a CI run never resolves
its own dependency set. Regenerating the lock is `make lock`, a deliberate
commit with a changelog note, never a side effect of another target.

pip-compile rather than uv: the specification names either a `uv.lock` or a
`requirements.lock` and does not decide between them. pip-tools produces a plain
`requirements.txt`-shaped file that `pip install -r` consumes with no additional
tool on the runner, which keeps the CI install step free of a second package
manager.

### Report engine: latexmk with TeX Live

TeX Live 2025 is already installed on this machine in full, with `latexmk`
version `4.87` available at `/usr/bin/latexmk`. That is precisely the fallback
condition the specification names, so the fallback is taken: the resolved engine
is `latexmk`.

`tectonic` version `0.16.9` is also present at `/usr/local/bin/tectonic` and was
considered. It is rejected here for the reason the specification gives for
preferring it in the first place, read the other way: tectonic's advantage is
that it avoids installing a multi-gigabyte distribution, and on a machine that
already carries one that advantage is zero while the cost of maintaining a
second toolchain is not.

`make reports` wraps the resolved command so the target is the same either way.
No report is built at P0; the sources are authored at P7.

### `ml-experiment-triage` is not yet a dependency

It is deliberately absent from `pyproject.toml` at P0. P5 is the phase that
integrates it, and adding it now would put a dependency in the lock file that
nothing imports.

There is a real obstacle to record while it is fresh: **the package is not
published on PyPI.** It exists only as a GitHub repository. P5 may pin a
pre-release from a git tag, but tagging `v1.0.0` here while any dependency is a
git ref rather than a released version is forbidden by the specification, so
publishing that package to PyPI is a blocking cross-repo task with a deadline of
this project's first stable release. It is filed in
`docs/cross-repo-tasks.md` with status open.

## Consequences

- Every version above is reproduced in `pyproject.toml` as a lower bound and in
  `requirements.lock` as an exact pin, and will be reproduced again inside every
  result manifest from P5 onward.
- A dependency upgrade is a deliberate `make lock` commit, visible in review.
- `requires-python` at `>=3.14` narrows the install base to machines with a
  current interpreter. This is the honest claim given what CI tests, and it is
  revisited when a matrix entry exists to justify widening it.
- Choosing latexmk means the report build depends on a TeX Live installation
  that this repository does not provision. P7 records the exact packages the
  three documents need so that a machine without TeX Live can reach the same
  result with tectonic instead.
- The unpublished evaluation harness is the one dependency risk that cannot be
  resolved inside this repository, and it is tracked rather than deferred.
